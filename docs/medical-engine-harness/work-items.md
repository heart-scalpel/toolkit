## 2. 每项到底做什么

以下“新增路径”均为建议位置，开发时可以按现有模块结构调整，但职责和产出契约不可省略。跨工具通过文件、命令或正式API交换数据，保持独立虚拟环境。

### W00 — 先明确代码事实和所有权

- 落点：`cozy_agent/AGENTS.md`、`README.md`、`backend/app/agents/factory.py`；本目录架构文档。
- 工作：纠正文档中工厂仍是占位实现等过时描述；确认Gateway负责生命周期、SDK负责执行循环、共享能力不依赖具体医生；明确哪个仓库拥有输入Schema和资产协议。
- 输入/产出：实际代码清单 → 一份批准的组件责任表与依赖方向。
- 验收/关闭：现有启动、工厂和业务接线与文档一致；依赖方向有适度静态检查。不得用这项任务重建已有RAG/审核服务。借鉴DF01、DF02。

### W01 — 冻结生成和被审核版本

- 落点：`langfuse-toolkit/app/projects/playground.py`、`output-collector-toolkit`的合并/导出接口、`annotation-toolkit`的上传与导出；新增数据快照清单。
- 工作：运行时收集实际Prompt版本、模型参数、Schema和Output摘要；形成GenerationRun、CaseRevision、DraftRevision。修改同一case_id的内容必须产生新revision，旧审核继续指向旧版本。
- 输入/产出：源100条、分类run.json、医生50条 → 逐条来源关联和缺失历史信息清单；新批次产出完整清单。
- 验收/关闭：当前50条问题/画像与源数据逐条等价；缺失或重复关联报错；改一项事实后不能继承旧审核。旧生成Prompt版本缺失保留null。借鉴DF07、DF10。

### W02 — 输入契约和无损回放

- 落点：`prompt-agent/app/safety_classifier.py`；`cozy_agent/backend/app/agents/lactation/models.py`及输入组装；新增受版本控制的咨询输入Schema与适配器。
- 工作：从原始JSON恢复审核关联输入；保留精确日龄、主体、背景原文、用户目标与字段来源；区分未知、否认和冲突。显示Markdown只用于阅读。
- 输入/产出：CaseRevision → canonical consultation input + 两个阶段的实际字段选择/hash。
- 验收/关闭：50条可导入；null不变成0；日龄不丢失；用药主体歧义不被猜改；人工标签和批注不进入被测载荷；线上与回放的输入适配对同样fixture等价。借鉴DF02、DF05。

### W03 — 审核是一组编辑操作和判断

- 落点：`annotation-toolkit/app/profiles/cozie_medical_review.py`、审核规范；`review-query-toolkit/app/evaluation.py`旁新增反馈提取/导出模块。
- 工作：保留原始响应，新增replace/amend/delete/comment/reference_previous语义和原文锚点；区分分类解释、修改指令和完整修订结果；多命题拆分为FeedbackItem。
- 输入/产出：ReviewResponse → 有来源的反馈项、结构问题和待确认问题。
- 验收/关闭：覆盖ACCEPT+意见、REVISE无编辑、删除追问、空值和“同上”；不会把空白当删除或批注当定稿；同一导入重跑不新增重复反馈。借鉴DF06、DF07。

### W04 — 分类、素材、输入和方法分别裁决

- 落点：标注平台新增裁决表单/Schema、`review-query-toolkit`状态筛选；具体存储方式可先用版本化JSONL。
- 工作：先处理S13-Q003主体歧义、S04-Q006动作解释、S05-Q006用户目标；再处理CLEAR共选、专家请求和EXCLUDE语义。裁决不得覆盖原始审核。
- 输入/产出：FeedbackItem + 明确待答问题 → Adjudication及四条独立状态轴。
- 验收/关闭：每个问题有明确决定、责任角色、原文依据和时间；未知继续pending且列出下一步；修改题目后重审；不凭分类标签自行调整医疗处置。借鉴DF06、DF09。

### W05 — 只评估实际使用的分类器

- 落点：`prompt-agent/classify.py`及`cozy_agent/backend/app/agents/shared/safety_classifier.py`、工厂适配入口。
- 工作：建立从独立进程调用业务分类组件的离线入口，或者让双方调用同一正式组件；统一所选字段与资产解析；分别输出模型原类、失败回退、平台下限、最终策略。
- 输入/产出：规范输入+精确资产配置 → 可对照的分类结果与执行状态。
- 验收/关闭：同一fixture两个入口的模型请求等价；分类服务异常、平台风险下限各有可定位结果；用实际同源实现重跑已审定集并重新报分母。随机输出不能通过“逐字相同”验收，确定性载荷才应完全一致。借鉴DF01、DF02、DF10。

### W06 — 发布基线，不把筛选当裁决

- 落点：`review-query-toolkit`新增基线导出器和清单；复用现有evaluate计算。
- 工作：分类标签、回复要求、追问要求各自依据确认状态导出；保存纳入/暂缓/排除理由和source family。当前42条只是规则筛选集，当前50条归开发/诊断集。
- 输入/产出：来源版本+裁决记录 → EvalSetRevision及样本索引。
- 验收/关闭：每条标准有被审版本和确认人；未决问题不混入已确认字段；零样本不报通过；同family/pair不跨开发与留出集。借鉴DF10。

### W07 — 问题生成修复输入问题，承担覆盖责任

- 落点：`langfuse-toolkit/prompts/questions.system.txt`、`questions.user.txt`、对应Schema/definition；收集器校验。
- 工作：针对已裁决的主体、目标和事实冲突补生成约束；明确有意构造的信息不足案例与意外错误；对照组的changed_factor必须真实且只有预定差异。
- 输入/产出：已确认source问题+覆盖计划 → 新Prompt版本、新来源明确的案例revision。
- 验收/关闭：问题不包含答案/期望标签；组内事实差异符合计划；给出18场景及分类支持数覆盖报告；对修订题重新生成、审核。不能仅看JSON合法率。借鉴DF07、DF10。

### W08 — 候选材料与线上回复共用原则，保留输出差异

- 落点：`langfuse-toolkit/prompts/review.*`；`cozy_agent/backend/app/agents/lactation/prompts/builder.py`和`system.md`。
- 工作：将已确认公共要求通过统一资产版本装配到两个入口；候选生成仍输出初步判断、回应方向、0–2条有目的追问；线上生成面向用户的完整答复。
- 输入/产出：同一案例+已批准资产 → DraftRevision和实际回复，分别评测。
- 验收/关闭：不把“可先说明……”方向说明原封不动给用户；不强凑追问；医生改动可定位到模板/规则资产；生成器候选标签不充当评测裁判。借鉴DF02、DF03。

### W09 — 提取公共咨询流程

- 落点：业务公共过程模块、提示词构建器与评测rubric；C01–C04为首批候选。
- 工作：明确当前诉求、已知事实、本人目标、信息缺口；每个追问对应会改变的决定；无必要可不追问。先用结构化规则和一个SDK Run组织，不预设增加多个模型调用。
- 输入/产出：规范输入 → 咨询任务要求/过程约束及对应正反例。
- 验收/关闭：同一安全标签下仍能分辨“没回答”“重复问”“违背目标”；C04中S05-Q006先经裁决；确认过的明确风险响应不能被交流规则延后。借鉴DF01、DF02、DF05。

### W10 — 医生方法有条件、有版本、有撤回

- 落点：新增DoctorMethod资产注册表和选择器；业务工厂可信配置指定医生及批准版本。
- 工作：对D01–D03分别请医生确认稳定性和适用条件，拆离知识主张；C05先按专科共享候选处理。首轮只选一张条件明确的方法卡试验。
- 输入/产出：原文锚点+公共基线+知识依据 → proposed/reviewed/pilot/approved方法revision。
- 验收/关闭：proposed不能加载；未选中方法不进入上下文；医生方法不能扩大工具权限或降低安全约束；同输入对比公共基线与加方法的盲评、反例和禁用实验。单医生样本不能证明独有性。借鉴DF03、DF04、DF08。

### W11 — 医学知识从风格和工具日志中独立出来

- 落点：知识库条目管理；`cozy_agent/backend/app/agents/lactation/tools/knowledge.py`与RAG结果协议。
- 工作：对K01/K02、D01/D02中的知识部分建立来源、条件、有效日期与专业审定；内部保留doc_id、chunk_id、文档版本和请求引用；检查回答主张与证据是否对应。
- 输入/产出：待审知识主张+专业来源 → KnowledgeRevision和可追踪的检索证据。
- 验收/关闭：能回到确实返回过的片段；空/无关/冲突结果有明确处理；有检索命中不自动判医学正确；不把一段医生批注直接当公共知识。借鉴DF07；领域审定是额外责任。

### W12 — 真实运行时回放和多维验收

- 落点：新增独立回放入口，调用`cozy_agent`实际factory/业务组件；`review-query-toolkit`扩展实验结果汇总。
- 工作：固定base/candidate bundle、输入集、模型参数和裁判版本；分类、诉求完成、目标尊重、追问、证据、安全、费用/延迟分别报告。先固定RAG fixture测组件，再单列真实RAG实验。
- 输入/产出：实验协议+EvalSetRevision → 每条结果、配对变化、失败和汇总。
- 验收/关闭：所有调用失败留在总分母；零样本不PASS；规定修复点通过且受保护回归不退化；质量门槛在运行前登记，医生方法使用身份盲评。不得把`expected_contains`或文本相似度当医学合格。借鉴DF06、DF07、DF10。

### W13 — 发布的是整套版本，不只是Prompt标签

- 落点：Langfuse现有版本/标签命令、业务配置和发布流程；新增ReleaseBundle清单。
- 工作：固定策略、模板、公共组件、医生方法、知识和模型/Schema版本；通过试验后更新可信配置；记录实际加载版本与上一个包。
- 输入/产出：通过的ExperimentRun → 发布回执、运行trace引用及可执行回滚路径。
- 验收/关闭：标签移动后老实验仍能解析旧内容；新请求记录的是实际包；回滚演练恢复精确旧包；报告“已验证”与“已生效”区分。借鉴DF07、DF10。

### W14 — 验证流式过程中用户实际看到了什么

- 落点：`cozy_agent/backend/app/agents/lactation/agent.py`、输出审核和客户端事件处理。
- 工作：回放规则拦截、语义拦截、工具失败、取消/重连；记录首次暴露内容、撤回事件、安全替代文本和最终状态；根据实际结果决定哪些分支需要缓冲输出。
- 输入/产出：有事件顺序的运行fixture → 最终结果与暴露/撤回证据。
- 验收/关闭：最终回复权威唯一；撤回后无旧正文继续追加；禁止的内容即使最终被替换，也计入曾暴露指标；缓冲策略另报告延迟代价。借鉴DF02、DF07、DF09。

### W15 — 从反馈走到线上结果才算闭环

- 落点：`review-query-toolkit`反馈任务查询、现有Langfuse追踪metadata与实验记录。
- 工作：串联response→feedback→adjudication→任务→资产版本→实验→发布→运行；不重建现有追踪系统。保留拒绝、被替代、等待医生的状态和原因。
- 输入/产出：各阶段ID/回执 → 一个可查的闭环记录。
- 验收/关闭：随机选一条反馈能定位实际改动和结果；只改文档或完成离线分析的项目标记offline_only；发布后未验证使用情况不标observed_closed。借鉴DF06、DF07、DF09。

### W16 — Prompt维护归属和装配快照

- 落点：`langfuse-toolkit/prompts/definitions/`和现有Prompt发布模块；业务builder与离线入口。
- 工作：明确问题生成、材料生成、安全分类、线上回复和审核器各自的唯一维护归属；本地声明与远端版本同步只选一种主源流程。运行记录resolved版本及组合后的hash。
- 输入/产出：资产责任表 → Registry/Bundle协议和同步操作说明。
- 验收/关闭：不能同时手改两份分类Prompt而无校验；现有create_version/assign_labels读回能力继续复用；离线文件hash与线上加载hash可核对。借鉴DF02、DF03、DF10。

### W17 — 长任务持久化，等待人工时结束Run

- 落点：现有离线CLI/收集器任务状态；先使用适合现有规模的文件或数据库记录。
- 工作：条目有幂等键、attempt、状态和结果引用；中断后只恢复未完成项；待医生事项持久化并结束模型Run，回复到达后创建关联的新Run。
- 输入/产出：批次清单 → 可恢复的逐条结果与待办。
- 验收/关闭：中断续跑不重复导入审核、不覆盖旧版本；失败可重试且结果可追溯；不会靠LLM循环等待。以后需要并行委派时再加入DF06报告契约，首版不要求多Agent。借鉴DF09。

### W18 — 补充独立留出覆盖

- 落点：场景覆盖计划、questions生成参数、采样与评测清单。
- 工作：补S14缺口、当前没有人工样本的non_health和少量类别；补齐成对输入，固定family/pair分组；根据要验证的风险边界和方法条件设计新案例。分类标注先隐藏候选/引擎标签独立判断，再进入差异裁决；素材质量另行审核。
- 输入/产出：冻结的改进假设/覆盖计划 → 未参与规则提取的新留出集。
- 验收/关闭：报告每类和每场景实际支持数；成对案例有完整输入且不跨集合；不靠重复改写当前50条冒充独立样本；样本不足明确说明，不能宣称可靠性已证明。借鉴DF10。

## 3. 第一个可交付切片

建议先完成一个从数据到评测的完整切片，再扩大方法库：

1. W00/W16确定归属；W01/W02恢复50条原始JSON并建立revision，W03登记原始反馈。
2. W04解决关键歧义；W06发布有明确状态的开发基线；W05完成真正分类入口的回放。
3. 选C01/C02作为公共改进、D01作为需要医生确认的对照候选；先完成必要W11知识确认，再落实W09/W10和W08。
