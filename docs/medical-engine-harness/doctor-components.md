# 医生方法与公共组件：如何区分和提取

## 1. 先拆一条意见，再谈共享范围

医生反馈可能同时包含“患者事实判断、医学知识、技术选项排序、交流偏好、修改这一条的指示”。这些内容的验证方式和作用范围不同，必须拆成原子记录，不能把整段医生批注当作Skill。

例如 S03-Q005 的意见至少有三个不同命题：先承接妈妈情绪；优先介绍某一种哺乳姿势；认为另一种姿势在特定条件下难操作。第一项可能是公共交流流程，第二项是医生方法候选，第三项涉及技术适用性，需要专业证据。三项不能一次性全变成公共规则，也不能仅因来自同一位医生就全标为“独到理念”。

## 2. 归属判定表

| 类别 | 判断标准 | 储存和执行位置 | 确认要求 |
| --- | --- | --- | --- |
| 平台公共机制 | 与医生身份和专科知识无关，如版本、隔离、工具真实回执 | Harness/公共代码 | 工程契约与测试 |
| 公共咨询流程 | 回答当前问题、使用已知信息、尊重目标、必要且中性的追问 | 公共Procedure/结构化检查；Prompt渲染只是载体 | 产品约束+代表案例验证；临床相关分支另需专业审定 |
| 专科共享方法 | 泌乳咨询常用的观察、解释与信息采集顺序 | 母婴/泌乳领域组件 | 适用人群、必要输入、专业审核、正反案例 |
| 医生方法候选 | 在同样安全和事实约束下，医生选择的技术优先序、沟通顺序或表达偏好 | `DoctorMethod` 版本资产 | 该医生确认“这是稳定方法还是此例特例”；盲评/对照验证 |
| 医学知识主张 | 可真可假、依赖人群和条件的知识、操作方式、阈值 | 有来源的Knowledge资产 | 证据与适用条件确认；不以“这是风格”豁免核验 |
| 单例编辑/未决问题 | “同上”、改一个词、引用上一版本、存在输入歧义 | Feedback与裁决记录 | 补全原意，未确认前不抽取为运行规则 |

**“来自医生”描述来源，“为医生独有”描述差异性，“可公共复用”描述验证后的适用范围，三者是不同字段。** 一位医生重复提出某意见也只能增加其偏好一致性的证据，不能证明独创或医学正确。

本批只有1位医生，首批只能提出3类医生方法候选；没有足够证据宣布任何一类为其独有。识别差异的方法是让其他医生在同一输入、相同安全与知识条件下独立给出偏好，比较其条件分支和排序，并由原医生解释其取舍。不能简单把多数票当医学事实。

| ID | 观察与归属建议 | 代表用例 | 需要做什么 | 回归/反例 |
| --- | --- | --- | --- | --- |
| C01 | 公共流程：优先解决当前明确问题 | S10-Q004、S04-Q005、S07-Q001 | 把“用户要解决什么”显式列入评测；检查回复是否遗漏主问题，W09/W12 | 直接答复普通问题；遇明确风险不能为直答而越界 |

## 4. 医生方法卡应是什么样

以 D01 为例，卡片首先应是下面的审定对象，而不是立即可运行的提示词：

```json
{
  "method_id": "D01",
  "owner_doctor_id": "medical_reviewer_01",
  "claim_kind": "technique_order_preference",
  "scope": "doctor_candidate",
  "status": "proposed",
  "evidence_case_ids": ["S03-Q005"],
  "proposed_intent": "在相关情境中优先介绍医生偏好的抱姿选项",
  "activation_conditions": "待医生确认",
  "contraindications_and_exceptions": "待专业确认",
  "shared_dependencies": ["goal-respect", "safety-policy", "verified-positioning-knowledge"],
  "cannot_override": ["safety_policy", "user_goal", "tool_permissions"],
  "approved_revision": null,
  "runtime_enabled": false
}
```

“先安抚”“按某顺序追问”如果没有明确触发条件，会变成新的机械模板。因此每张卡还需要：适用/不适用案例、必要输入、输出目的、选择的备选路径、原始证据锚点、批准记录、依赖版本、回归用例和撤回原因。

## 5. 从候选升级到公共组件

建议采用可审计的状态机：

`proposed → evidence_pending → reviewed → pilot → approved → deprecated/revoked`

状态含义：

- proposed/evidence_pending：模型或分析者提出，不能装入线上资产包。
- reviewed：医生确认了含义和范围；涉及知识真伪的部分已有专业证据记录。
- pilot：固定条件下进行离线/受控比较，尚不能作为公共默认。
- approved：组件负责人和对应专业审核确认，所需回归完成，发布包引用准确版本。
- deprecated/revoked：不再用于新请求；历史trace保留旧版本引用，能说明撤回原因。

公共化的必要证据是：概念和条件清楚、有跨场景复用价值、不依赖这一个用户、知识证据充分、跨医生比较未显示不可合并分歧、移除医生身份后仍能通过任务/安全测试。**出现跨医生偏好差异时保留可选择的方法，不用一个平均Prompt抹平它。**

## 6. 不应进入医生方法层的内容

- 未决的用药、发热、储存、清洁等医学/护理判断不能包装为个人风格。
- 用户“不想加泵”的目标属于用户上下文，不属于医生默认策略。
- RAG命中、工具执行成功、已产生的最终输出属于运行证据，不属于可自由改写的记忆。
- 原始审核批注只作为证据。只有被批准的规则内容才能进入受信任资产；读取一条医生评论不会使其自动获得系统指令权限。
- 本批评审已被用于提取规则，后续证明泛化能力需要新的留出案例和完整对照组。

这对应 DeerFlow 的“可发现的资产、实际激活的资产、执行时的权限”三者分离。用于医生方法时，还要增加领域证据与审定状态，不能仅创建一个SKILL文件就视为完成。
